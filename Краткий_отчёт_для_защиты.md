# Краткий отчёт для защиты

## Тема и цель

Практическое занятие посвящено параллелизму, конкурентности и ограничению GIL
в Python.

Цель — сравнить четыре способа выполнения смешанной CPU-bound и I/O-bound
нагрузки и определить, когда использовать потоки, процессы или `asyncio`.

## Исходная задача

В варианте 1 есть две независимые части:

1. `cpu_job` — математические вычисления в большом цикле. Это CPU-bound
   нагрузка.
2. `io_job` — ожидание через `time.sleep`. Это I/O-bound нагрузка.

Также есть `io_job_async` с `asyncio.sleep` и эталонная функция
`run_sequential`.

Все задания независимы: результат одного задания не нужен для запуска другого.
В конце CPU-результаты складываются, а для I/O проверяется количество ответов.

## Что было сделано

Исходный [variant_1.py](./variant_1.py) не изменялся. Дополнительные решения
написаны в [variant_1_parallel.py](./variant_1_parallel.py):

* последовательная модель — эталон;
* `run_threaded` — выполнение в потоках;
* `run_processes` — CPU-задачи в отдельных процессах, I/O-задачи в потоках;
* `run_asyncio` — асинхронные ожидания, CPU-часть вынесена через
  `run_in_executor`;
* измерение медианы и диапазона времени;
* расчёт ускорения и оценка по закону Амдала;
* проверка совпадения результатов.

Тесты находятся в [test_variant_1_parallel.py](./test_variant_1_parallel.py).

## Методика

Для каждого размера задачи выполнялся один прогревочный запуск, затем 5
измерений. Первый запуск не учитывался. Время генерации входных данных не
включалось.

Использовались размеры `scale=1`, `scale=4`, `scale=8`.

Компьютер: Windows 11, Intel Core i9-14900HX, 24 физических и 32 логических
ядра, 31.73 ГБ ОЗУ, Python 3.13.2.

## Объяснение результатов

### Почему потоки помогают?

Потоки хорошо перекрывают ожидания. Во время `sleep` процессор не занят, а GIL
освобождается. Поэтому I/O-задачи могут выполняться одновременно.

### Почему потоки не дают большого ускорения CPU?

В стандартном CPython действует GIL: в один момент времени только один поток
исполняет Python-байткод. Поэтому чистые Python-вычисления в потоках не
распараллеливаются по ядрам.

### Почему процессы быстрее на больших размерах?

У каждого процесса свой интерпретатор и свой GIL. Поэтому несколько
`cpu_job` могут выполняться на разных ядрах. На больших задачах выигрыш
перекрывает стоимость запуска процессов и передачи данных.

### Почему процессы не всегда лучшие?

У процессов есть накладные расходы:

* запуск и завершение;
* сериализация аргументов и результатов;
* межпроцессное взаимодействие;
* дополнительная память.

На маленькой задаче эти расходы могут почти полностью убрать ускорение.

### Зачем нужен `asyncio`?

`asyncio` эффективен для большого количества неблокирующих ожиданий. Он не
ускоряет CPU-вычисления, поэтому CPU-часть была вынесена через
`run_in_executor`, чтобы не блокировать event loop.

## Закон Амдала

Формула:

\[
S(p) \leq \frac{1}{f + (1-f)/p},
\]

где `f` — последовательная доля работы.

Так как задания независимы, идеальная граница при `f=0` равна:

| Исполнители | Идеальное ускорение |
|---:|---:|
| 2 | 2x |
| 4 | 4x |
| 8 | 8x |

Реальные значения меньше из-за GIL, запуска процессов, планирования, обмена
данными и других накладных расходов.

## Проверка корректности

Результаты всех моделей сравнивались с `run_sequential`. Вещественная сумма
сравнивалась с допуском `1e-12`, количество I/O-ответов — точно.

Результат:

```text
Ran 2 tests

```

## Итоговый вывод

Для этой задачи выбор зависит от размера и характера нагрузки:

* маленькая смешанная задача — `asyncio` или потоки;
* блокирующее I/O — потоки;
* много неблокирующего I/O — `asyncio`;
* большие независимые CPU-вычисления — процессы.

В моей работе на `scale=1` лучшим оказался `asyncio`, а на `scale=4` и
`scale=8` — пул процессов. Это подтверждает, что универсального способа
параллелизации нет: нужно учитывать GIL, тип нагрузки и стоимость запуска
исполнителей.

## Возможные вопросы преподавателя

**Почему не изменялся исходный файл?**  
По условию эталонный код и `run_sequential` нельзя изменять, иначе сравнение
было бы некорректным. Поэтому дополнительные реализации вынесены в отдельный
файл.

**Почему первый запуск не учитывался?**  
Первый запуск может быть медленнее из-за импорта модулей, создания пулов и
подготовки интерпретатора. Это снижает влияние прогрева.

**Почему реальное ускорение меньше закона Амдала?**  
Закон Амдала даёт идеальную верхнюю границу. В реальности есть GIL,
планирование, запуск процессов, сериализация и конкуренция за ресурсы.

**Почему эффективность не равна 100%?**  
Ускорение делится между несколькими исполнителями, но часть времени уходит на
накладные расходы и последовательные операции. Поэтому добавление исполнителей
не даёт пропорционального ускорения.

**Все ли результаты корректны?**  
Да. Суммы CPU-вычислений совпали с эталоном с относительным допуском `1e-12`,
а количество I/O-ответов совпало точно.
